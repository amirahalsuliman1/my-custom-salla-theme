# DERIVED DECISIONS — visual calls made without a design reference

**Authorised by the project owner on 2026-08-05**, when B4, B7 and B8 were closed by derivation rather than by new artboards.

Every visual decision taken **without** an artboard specifying it is recorded here. The register exists so that a reader can always tell the difference between *the design said this* and *we worked this out ourselves* — and so that if Design later supplies the missing screen, the delta is a lookup, not an archaeology project.

An unrecorded inference is indistinguishable from an invention. Record it.

---

## What must be recorded

- Any layout at a breakpoint above 393pt — every one, since no artboard exists above mobile (B4).
- Any screen built without an artboard: search results, category listing, empty states, 404 (B8).
- Any reading of an unnamed or ambiguous artboard: `Full_Page.pdf`, `Ariana_Grande.pdf`, the partner pair, the redemption pair, the `Notification` trio (B7).
- Any semantic token added on top of the shipped Tailwind scales (B2).

## What must **not** be recorded here

- Anything an artboard specifies directly. That is implementation, not derivation.
- Technique A/B/C override choices. Those belong in [OVERRIDES.md](OVERRIDES.md).
- A screen may well need a row in **both** files — a derived screen that also shadows an upstream Twig has an entry here for its visual choices and a row there for the shadowed file.

## Standing rulings these rows inherit from

Recorded once here so individual rows do not restate them.

**B4 — breakpoint derivation.** The 393pt design binds content, order and hierarchy. Above it, only five moves are permitted: bounded centred container; grids gain columns while the card is unchanged; bottom sheets become centred dialogs above tablet; footer goes multi-column; spacing and type scale up through the Tailwind scale. Adding an element absent from mobile, reordering content, or hiding content that exists on mobile is forbidden at every breakpoint.

**B7 — unnamed artboards.** Treated as additional states, never as alternatives. Implement every state a file shows. Never pick one file and discard the others.

**B8 — missing screens.** Built from existing components and upstream Twilight templates in the established visual language: warm page background, white cards, subtle borders, the same buttons. No new visual pattern is invented.

### AC-9 — The sign-in sheet is this theme's; the three steps inside it are Salla's

**Ruled 2026-08-10 by the project owner, under T-5.01, after the finding below was put to them.**

**The finding, read in the component's source and not assumed.** `salla-login-modal`'s entire `render()` is an `<iframe>` whose `src` is `accounts.salla.com`, wrapped in a `<salla-modal>`. Its only channel to that document is `postMessage`, and `isTrustedMessage()` validates the origin strictly. **The method choice, the identifier field and the verification code are Salla's pages on Salla's origin.**

That falsifies T-5.01's own technique line — «`salla-login-modal` — technique C preferred, B if presentation cannot be overridden». **Neither is available.** CSS does not cross an origin boundary, and a subclass reaches the modal shell, never the document inside it. No amount of either produces `SignIn Bottom Sheet Step 1.pdf`.

**The alternative that was rejected, and why it was offered at all.** `salla.auth.api` exposes `login()`, `verify()`, `resend()` and `register()` as typed public SDK surface. It was rejected because it silently drops three things that live inside the iframe and that **no artboard draws**:

- **Passkeys / WebAuthn.** The iframe carries `allow="publickey-credentials-get; publickey-credentials-create"` and an `open_passkey_page` action opening `${login.url}/create-passkey`.

- **New-customer registration.** `verify()` can answer `case: 'new_customer'`, which requires `register({ first_name, last_name, … })`. **There is no name-capture artboard**, and B8's derivation list does not cover one.

**The cost that was accepted.** The **shell** matches the artboard — a bottom sheet on T-2.10, the «تسجيل الدخول» heading, the ✕, the rise, the above-tablet centred dialog, and all four of the accessibility behaviours the platform's own modal lacks. **The contents do not.** The segmented «رسالة نصية / البريد الإلكتروني» choice drawn in Step 1, the identifier field in Step 2 and the code entry in Step 3 render as Salla's pages and will not look like the exports. Nothing in `04-components/login-sheet.scss` can change that, and a future task must not try — a selector that appears to work would mean the flow had stopped being an iframe, which is a change to report, not to build on.

**What this obliges.** The theme owns the sheet, its heading, its close control, its reserved height and its bounded width above tablet. It owns no field, no label, no validation and no submission. **T-5.02 and T-5.03 inherit this**: their acceptance criteria about country codes, `autocomplete`, resend timers and rate-limit messages are the platform's behaviour to verify and record, not the theme's to build. Carried by [T-5.01](19-ENGINEERING-BACKLOG.md).

### AC-2 — Form controls have no success state

### OP-11 — reordering cannot say which items it failed to add

**Raised 2026-08-11 under T-6.04.** The task's criterion is that unavailable or out-of-stock items be «reported rather than silently dropped». The platform does not report them.

**What the API gives.** `salla.order.createCartFromOrder(order_id)` resolves to `CreateCartFromOrderResponse`, whose `data` is `{cart_id, url}`. Nothing enumerates what could not be added. The events — `onOrderCreated` and `onOrderCreationFailed` — carry the same response and a `RequestError` respectively. **What was deliberately not built.** Comparing `order.items|length` with the created cart's `count` and announcing the difference. **Three ways forward:**

1. **The platform already fills `data.message` for this case.** Then the criterion is met today and nothing more is needed. **Cheapest to check** — one reorder of an order containing an out-of-stock product, on a live store.
2. **Salla exposes the dropped items.** A `skipped` or `unavailable` array on the response would let the theme name them, which is what the criterion actually wants.
3. **The theme fetches the new cart and compares.** Only sound once the replace-or-merge question above is answered, and it costs an extra request on every reorder.

**This blocks nothing.** T-6.04 shipped, and reports whatever the platform says.

**Raised 2026-08-11 under T-6.01.** The status filter is drawn on all three orders artboards, with three options — «الطلبات السابقة», «طلبات قيد التنفيذ», «طلبات بانتظار الدفع» — and `Full Page.pdf` draws it open with the first one checked.

1. **Where the filtering happens.** No query parameter for the orders page is documented in the SDK types or the Salla docs, and **no Twig template in this theme or in upstream reads a query parameter at all** — there is no `request`, no `query`, no `app.request` anywhere in `src/views`. `salla.order.api.fetch` does accept `status`, but as an array of **numeric ids**, which are per-store and unknowable from a theme. So the filter runs in the browser, over the cards already rendered.
2. **What each group means.** No status is called «سابقة». The grouping is `is_pending_payment` → بانتظار الدفع, else `can_cancel` → قيد التنفيذ, else سابقة.

**Both costs are real and both are visible rather than silent.** The filter groups what is loaded, so with more orders than one page holds a group can look emptier than it is until the rest arrive — `order-list.js` re-applies on every append, which narrows it but does not close it. And a store that forbids cancellation leaves `can_cancel` false on every order, which files all of them under «الطلبات السابقة». **A wrong grouping is a worse outcome than a slow one, and it is the reading that most wants an owner's answer.**

**Three ways forward:**

1. **Salla names a parameter for this page.** Then the filter becomes a link, the pagination question disappears, and the grouping question moves to the platform where it belongs. **This is the first thing to ask.**
2. **The merchant maps statuses to the three groups**, as a theme setting. It removes the guess and adds a setting a merchant must maintain — the trade AC-1 already accepted for hotspots and Stories.
3. **The groups are redefined against something the order always carries**, if the owner would rather change the design than the data.

**This blocks nothing.** T-6.01 shipped with the flag-based rule and re-filters on append.

### OP-7 — the birthdate picker is drawn as a wheel sheet with a Hijri tab, and the component is a month grid

**Why this was not simply built.** Two reasons, and the second is the heavier one.

2. **A Hijri tab is a calendar conversion, and nothing in the platform supplies one.** The theme would own a Gregorian↔Hijri algorithm — including the divergence between tabular and observational variants — and it would own it **on a birthdate**, where being one day out is wrong forever and silently. **What shipped.** The calendar in the theme's language — surface, trim, focus ring, and a selected day distinguished by fill where today is a ring — plus the locale fix, which was the defect that actually mattered: the calendar had been rendering in English on Arabic storefronts.

**Three ways forward:**

1. **Ask Salla whether `salla-datetime-picker` supports a Hijri locale.** flatpickr has an `ar` pack but no Islamic calendar; if the platform has an answer, it is theirs and cheap. **This is the first thing to check.**
2. **Build the wheel sheet on T-2.10's primitive, Gregorian only.** The sheet, the three wheels and the two actions are all reachable; **the «هجري» tab would be drawn and dead**, which is worse than not drawing it.
3. **Accept the month grid.** It is keyboard-navigable, localised, and correct — and a birthdate is entered once.

**This blocks nothing.** T-5.05 shipped without both, and no later task depends on the wheel.

### OP-6 — the loyalty balance's rate and expiry have no data source

**Raised 2026-08-10 under T-5.10.** `Loyalty Points Page.pdf` draws two things this platform does not supply.

1. **«/ 1 ريال»**, beside the balance — the rate at which points convert to currency.
2. **«رصيدك الحالي من النقاط سينتهي قريبًا!»** with «استبدل نقاطك الآن قبل انتهاء صلاحيتها.» — a warning that the *balance* is close to expiring.

**What was checked, and came back empty.** The Twig `loyalty` object carries `name`, `description`, `image`, `promotion_title`, `promotion_description`, `points[]` and `prizes[]` — no rate, no expiry. `user.loyalty_points` is an integer. `salla.api.loyalty.getPoints()` requests `profile/loyalty/points` and the SDK reads `data.points` from it and nothing else. `salla.api.loyalty.getProgram()` requests `loyalty`, whose payload is not visible from the bundle. `/balance/points`, which `salla-loyalty-points-history` fetches, carries `expires_at` **per transaction** — the date one batch of points lapses, which is not the same fact as the balance expiring, and cannot be turned into the artboard's sentence without deciding what «قريبًا» means.

**Neither is built.** A conversion rate the theme computed, or a "soon" threshold the theme chose, would be a number on a customer's screen that nothing produced — and on a loyalty balance, a wrong one is a complaint rather than a cosmetic slip.

**Three ways forward, and they are not equivalent:**

1. **`getProgram()` carries them.** The most likely of the three and the cheapest to check — it needs a live storefront, not a code change. If the rate is there, the balance card gains it and nothing else moves.
2. **They are merchant copy.** The rate is a fact about the programme, so a theme setting for it would let a merchant state a number the platform is separately enforcing — **two sources for one truth**, which is the failure this project has recorded twice already.
3. **They are dropped from the design.** The balance card reads perfectly without the rate, and the expiry warning is the kind of thing a store emails rather than prints.

**This blocks nothing.** T-5.10 shipped without both; T-5.12's «Points Value Pop-up» may need reading 1 answered, and that task will say so if it does.

2. `.s-block` gains the panel treatment — the warm fill, the large radius, the inset — in **one** place, which is what makes this affordable at all.
3. The header's solid state and the footer become panels rather than bands.
4. **Contrast needs no new work.** The T-2.01 table above already measures every token against **both** `#F7F6F4` and `#FFFFFF`, because cards were always white. Nothing in it fails on either surface.
